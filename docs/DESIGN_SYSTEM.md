# Warehouse OS — سیستم طراحی مشترک

**این فایل منبع واحد حقیقت برای ظاهر هر سه بخش است:** اپ اندروید کارگر، پنل وب مدیر،
و اپ ویندوز فروشنده. هر پرامپتی که به یک هوش مصنوعی دیگر می‌دهی، باید این فایل را
همراهش paste کنی. اگر جایی این فایل با کد فعلی اختلاف داشت، **این فایل درست است**.

> **اصل حاکم:** اگر انتخابی بین «زیبایی» و «سرعت کاربر» باشد، سرعت برنده است.
> این همان قانون طلایی کل پروژه است (`docs/task-cards/android-operator-app-checklist.md`).

---

## ۱. رنگ

مقادیر پایه از `apps/android/.../ui/theme/Color.kt` می‌آیند و همان مقیاس Tailwind
(Slate + Blue) هستند. وب و ویندوز باید **دقیقاً** روی همین اعداد قفل شوند.

| نقش | مقدار | کاربرد |
|---|---|---|
| `primary` | `#2563EB` | کنش اصلی، فروش، خروج کالا |
| `primary-dark` | `#6EA8FE` | همان در حالت تیره |
| `success` | `#1A9951` | تأیید، ورود کالا |
| `danger` | `#E30117` | **فقط خطا و عملیات مخرب** |
| `warning` | `#B45309` (روشن) / `#F59E0B` (تیره) | نسیه، در انتظار، هشدار — در حالت روشن باید ≥ 4.5:1 کنتراست داشته باشد، پس amber-700 به‌جای amber-600 |
| `info` | `#7C3AED` | انتقال، چک در جریان |
| `text` | `#0F172A` | متن اصلی |
| `text-muted` | `#64748B` | متن ثانویه |
| `bg` | `#F8FAFC` | زمینه‌ی صفحه |
| `surface` | `#FFFFFF` | کارت و جدول |
| `border` | `#E2E8F0` | مرز و جداکننده |
| `surface-alt` | `#F1F5F9` | ردیف زوج جدول، زمینه‌ی فیلد |

### قواعد غیرقابل‌مذاکره

1. **قرمز فقط برای خطا.** «فروش» و «خروج کالا» آبی‌اند، نه قرمز. اگر قرمز هم یعنی
   «فروش» و هم یعنی «موجودی کم است»، هشدار واقعی دیده نمی‌شود.
2. **هیچ‌وقت فقط رنگ.** هر وضعیت = رنگ + آیکون + متن. دلیل: نور بد و انعکاس در انبار،
   و اینکه حدود ۸٪ مردها سبز و قرمز را سخت تفکیک می‌کنند — بدترین جفت ممکن برای
   «ورود» و «خطا».
3. **کنتراست حداقل ۴.۵:۱.** خاکستری کم‌رنگ برای اطلاعات مهم ممنوع.
4. **حالت تیره:** اندروید دارد. اپ ویندوز پیش‌فرض **روشن** است (مغازه روشن است).

### رنگ عملیات انبار

| عملیات | رنگ | نشانه |
|---|---|---|
| ورود کالا | `success` | ↓ |
| فروش / خروج | `primary` | ↑ |
| انتقال | `info` | ⇄ |
| انبارگردانی | `warning` | ⟳ |
| اصلاح | `text-muted` | ± |

### وضعیت‌ها (الگوی نقطه‌ی رنگی)

`در انتظار` warning · `تأیید شده` success · `باطل شده` danger ·
`نسیه/بدهکار` warning · `چک در جریان` info

## ۲. تایپوگرافی

- فونت: **Vazirmatn** در هر سه بخش.
- مبالغ و اعداد جدول: حتماً **tabular / عرض ثابت** (`font-variant-numeric: tabular-nums`)
  تا ستون اعداد فاکتور موقع تایپ نلرزد.
- حداقل اندازه‌ی متن روی اپ کارگر: ۱۶px. کارگر با دستکش و از فاصله می‌خواند.

## ۳. عدد و پول

**واحد پول کل سیستم تومان است.** در دیتابیس عدد صحیح بدون اعشار ذخیره می‌شود.

- نمایش: ارقام فارسی + جداکننده‌ی هزارگان → `۱٬۲۵۰٬۰۰۰ تومان`
- ورودی: **هم فارسی هم انگلیسی** قبول شود، و جداکننده حین تایپ خودکار درج شود.
  (همان منطق نرمال‌سازی `apps/api/src/common/phone.util.ts` — ارقام فارسی/عربی → انگلیسی.)
- تاریخ: شمسی با ارقام فارسی → `۱۴۰۵/۰۵/۱۲`
- هیچ‌جا «ریال» نوشته نشود.

> ⚠️ تغییر واحد به تومان **اعداد ذخیره‌شده را عوض نمی‌کند**. داده‌ی ایمپورت‌شده‌ی فعلی
> مشکوک است (بعضی ردیف‌ها قیمت خرید > قیمت فروش دارند، یعنی احتمالاً ریال وارد شده‌اند).
> پیش از اتکا به گزارش سود باید پاک‌سازی شود.

## ۴. دکمه‌ها

### اندازه

| بستر | ارتفاع | چرا |
|---|---|---|
| اپ کارگر (اندروید) | **۵۶px** | دستکش، حرکت، نور بد |
| اپ فروشنده (ویندوز) | **۴۴px** | کنش‌های اصلی، ماوس و کیبورد |
| پنل مدیر (وب) | **۳۶px** | کار اداری، تراکم بالاتر |

هیچ هدف لمسی زیر ۴۸px در اندروید نباشد.

### گونه‌ها

| گونه | ظاهر | کاربرد |
|---|---|---|
| `primary` | پرشده، آبی | یک کنش اصلی در هر صفحه — فقط یکی |
| `secondary` | مرزدار، خنثی | کنش‌های فرعی |
| `ghost` | بدون مرز | کنش‌های کم‌اهمیت داخل ردیف |
| `danger` | پرشده، قرمز | ابطال، حذف — همیشه با دیالوگ تأیید |

### قواعد

1. **در هر صفحه فقط یک دکمه‌ی `primary`.** اگر دو تا باشد، کاربر باید فکر کند — و فکر کردن یعنی کندی.
2. **هر کنش اصلی کلید میانبر دارد** و میانبر **روی خود دکمه** نوشته شده (`ثبت فاکتور F2`).
   این تفاوت واقعی سرعت با هلو است، نه گرافیک.
3. **حلقه‌ی فوکوس ۲px و واضح.** اپ فروشنده باید کامل با کیبورد قابل استفاده باشد،
   بدون اینکه کاربر گم شود کجاست.
4. **دکمه‌ی مخرب هرگز فقط آیکون نباشد** — متن داشته باشد.
5. **حالت در حال ارسال:** متن دکمه عوض شود («در حال ثبت…») و دکمه قفل شود تا دوبار ثبت نشود.
   هرگز دکمه بی‌صدا غیرفعال نشود.
6. **انیمیشن حداکثر ۱۵۰ms.** بدون skeleton درخشان، بدون ترنزیشن بین صفحات.

### میانبرهای پیشنهادی اپ فروشنده

| کلید | کار |
|---|---|
| `F2` | ثبت فاکتور |
| `F3` | جست‌وجوی کالا |
| `F4` | جست‌وجو / انتخاب مشتری |
| `F6` | تخفیف |
| `F7` | پرداخت |
| `F9` | ارسال لوکیشن به کارگر |
| `Esc` | بستن پنجره / انصراف |
| `Enter` | تأیید ردیف و رفتن به اسکن بعدی |

اسکن بارکد **نباید هیچ تپی لازم داشته باشد**: بارکدخوان خودش را کیبورد جا می‌زند،
پس فوکوس همیشه باید روی فیلد اسکن برگردد مگر کاربر عمداً جای دیگری باشد.

## ۵. گزارش‌گیری

گزارش‌ها باید **قوی** باشند، یعنی سه چیز: سریع باز شوند، قابل کندوکاو باشند، و قابل خروجی گرفتن.

### گزارش‌های لازم

| گزارش | محتوا |
|---|---|
| فروش دوره‌ای | مبلغ کل، تعداد فاکتور، میانگین فاکتور، به تفکیک روز |
| سود دوره‌ای | فروش منهای قیمت خرید لحظه‌ی فروش (`SaleInvoice.profit`) |
| بدهکاران | مانده‌ی نسیه به تفکیک مشتری، مرتب بر اساس بدهی |
| چک‌ها | سررسید نزدیک، وصول‌شده، برگشتی |
| پرفروش‌ها و راکدها | بر اساس ردیف‌های لجر `SALE` |
| موجودی زیر حد | کالاهایی که موجودی‌شان از `minStock` کمتر است |
| گردش انبار | ورود/خروج/انتقال در بازه، به تفکیک عملیات |
| عملکرد فروشنده | فروش و سود به تفکیک کاربر |
| تاریخچه‌ی خرید مشتری | داخل پروفایل مشتری |

همه‌ی این‌ها از `InventoryLog` و `SaleInvoice` قابل ساخت‌اند — ساختار داده آماده است.

### قواعد گزارش

1. **بازه‌ی پیش‌فرض «امروز»**، با دکمه‌های یک‌کلیکی: دیروز، این هفته، این ماه، ماه گذشته.
   کاربر نباید برای گزارش روزانه تاریخ انتخاب کند.
2. **هر عدد قابل کلیک است** و ردیف‌های زیرینش را باز می‌کند. گزارشی که نشود تهش را دید،
   قابل اعتماد نیست.
3. **ردیف جمع همیشه دیده شود** (چسبیده به پایین جدول، نه انتهای اسکرول).
4. **خروجی اکسل روی هر گزارش**، با همان سیستم قالب قابل‌تغییر (`ExportTemplate`).
5. **صفحه‌بندی سمت سرور** — هیچ گزارشی نباید کل ردیف‌ها را بکشد. کاتالوگ ۳۳ هزار قلمی است.
6. **حالت خالی معنادار**: «در این بازه فروشی ثبت نشده» + دکمه‌ی تغییر بازه — نه جدول خالی.
7. مبالغ با ارقام فارسی و tabular، تاریخ‌ها شمسی.

## ۶. الگوهای مشترک صفحه

- **کارت روی زمینه‌ی خاکستری** (`surface` روی `bg`) با فاصله‌ی سخاوتمندانه.
- **مسیر راهنما (breadcrumb)** برای درخت مکان‌ها: `انبار ۱ / طبقه ۲ / راهرو ۳` با «قبلی» درجا.
- **عملیات هم‌خانواده در یک کارت گروه شوند** (ورود / خروج / انبارگردانی کنار هم با رنگ و جهت).
- **جریان «عملیات اول، روش دوم»**: اول کاربر می‌گوید چه کار می‌کند، بعد از او پرسیده می‌شود
  با چه روشی (اسکن / لیست / صدا). صدا یک *روش* است، نه یک صفحه‌ی جدا.
- **RTL کامل** در هر سه بخش.
- هر صفحه چهار حالت دارد: بارگذاری، خالی، خطا، موفق. هیچ‌کدام جا نیفتد.
