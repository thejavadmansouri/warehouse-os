# تست End-to-End «کار انبار» (WorkTask) — ۱۵ اوت ۲۰۲۶

تست کامل سناریوی **POS → ارسال کار → تیک آفلاین در اپ → اتصال → sync → پیشرفت زنده** روی دستگاه واقعی و سرور واقعی.

## مراحل و نتایج

### ۱) ارسال از سمت POS (API) — ✅
`POST /work-tasks` با ۳ قلم، تخصیص به `staff_test`، یادداشت «تست E2E: برداشت ۳ قلم»:

| قلم | تعداد | وضعیت اولیه |
|---|---|---|
| بازویی برف پاک کن پیکان کاربراتوری | ۲ | PENDING |
| اب رادیاتور اب بان | ۱ | PENDING |
| چراغ جلو چپ سمندسورن مدرن | ۱ | PENDING |

**نتیجه:** `PENDING | 0/3` — idempotency هم چک شد: ارسال دوباره با همان `idempotencyKey` همان Task را برگرداند (نه تکراری).

### ۲) دریافت در اپ — ✅
لاگین `staff_test` → «کارهای انبار» → کار با **«۰ از ۳ آیتم — ۰٪»** + برچسب «در انتظار» + «درخواست: مدیر کل سیستم» نمایش داده شد.
جزئیات: هر ۳ قلم با نام، تعداد، SKU و آدرس قفسه.

### ۳) تیک آفلاین — ✅ (مهمترین بخش)
- `svc wifi disable` → پینگ به سرور: **Network is unreachable** (گوشی کاملاً از شبکهٔ انبار خارج شد).
- هر ۳ قلم تیک خورد → UI بلافاصله **«۳ از ۳ آیتم — ۱۰۰٪»** (پیشرفت محلی از outbox).
- کنترل سمت سرور: `GET /work-tasks/{id}` همچنان **`PENDING | 0/3`** — تیکها فقط در گوشی (Room + outbox) بودند، نه سرور. ✅

### ۴) اتصال و sync خودکار — ✅
- `svc wifi enable` → صبر چند ثانیه (بدون هیچ لمس اضافه).
- Worker پسزمینه (WorkManager با constraint شبکه) تیکها را به `POST /work-tasks/sync` فرستاد.
- سرور: **`COMPLETED | 3/3`** — هر ۳ قلم `DONE` با `doneBy: کارگر تست`.
- صف گوشی تخلیه شد (بنر «در انتظار همگامسازی» دیگر ظاهر نشد).

### ۵) پیشرفت زنده در POS — ✅ (بعد از رفع باگ)
`GET /work-tasks?warehouseId=…` (همان دادهای که پنل POS رندر میکند):

```
9fd2ad3c | COMPLETED | 3/3 (100%) | تست E2E: برداشت ۳ قلم
```

### ۶) وضعیت نهایی در اپ — ✅
دوباره وارد «کارهای انبار» → **«تکمیل شده» + «۳ از ۳ آیتم — ۱۰۰٪»** و جزئیات با هر ۳ قلم انجامشده.

## باگی که تست واقعی پیدا کرد و رفع شد 🔴→🟢

**مشکل:** در `SUMMARY_INCLUDE` بکاند (مسیر `GET /work-tasks/mine` و `GET /work-tasks` — همانهایی که پنل POS و لیست اپ میخوانند)، قلمها با `select: { id: true }` میآمدند — **بدون فیلد `status`**. `toTaskDto` با `items.filter(i => i.status === DONE).length` میشمارد، پس برای دادههای خلاصه همیشه `doneItems = 0` برمیگشت.

**اثر:** بعد از اینکه کارگر همهٔ قلمها را تیک زد، کار در جزئیات `3/3` بود ولی **نوار پیشرفت در پنل POS و لیست اپ صفر میماند** — دقیقاً همان چیزی که مدیر باید ببیند خراب بود.

**رفع:** `select: { id: true, status: true }` + ۲ تست رگرسیون در `work-tasks.service.spec.ts` (خلاصه با همهٔ DONE و خلاصه با پیشرفت جزئی).

**چرا تست واحد قبلی نگرفت:** تستهای سرویس Prisma را mock میکنند و این باگ فقط با رفتار واقعی Prisma (حذف فیلدها با `select`) بروز میکند — دقیقاً نمونهای از ارزش تست روی دستگاه واقعی.

## نکتهها / ملاحظات

1. **قانون «یک سشن فعال در هر حساب» تأیید شد:** وقتی برای چک API با `staff_test` لاگین گرفتم، سشن اپ باطل شد و اپ پیام «نشست منقضی شده» داد. این رفتار از قبل مستند است، نه باگ.
2. **کش محلی فقط بعد از refresh موفق بهروز میشود:** مقدار باگدار `0/3` تا لاگین مجدد و refresh در کش ماند — رفتار از قبل طراحی شده («آفلاین یعنی همان آخرین دادهٔ درست»).
3. **دادهٔ تست:** Task `9fd2ad3c-6986-4ca4-9697-0fb381083e8e` روی سرور dev باقی مانده (مرجع). در کنارش چند Task لغوشده از تستهای قبلی هست — قابل پاکسازی است.
4. **تست POS واقعاً در مرورگر انجام نشد** — پنل POS همان `GET /work-tasks` را میخواند که با curl تأیید شد؛ رویداد `work-task.progress` (بهروزرسانی زنده) با تست واحد + کد بررسی شده ولی چرخهٔ کامل مرورگر روی لیست بازنمانده انجام نشد.
