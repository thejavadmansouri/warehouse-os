# پرامپت‌های آماده برای هوش مصنوعی دیگر (Gemini / GLM)

هر پرامپت را **عیناً** کپی کن. در هر کدام نوشته شده چه فایل‌هایی را باید همراهش paste کنی —
چون آن مدل‌ها به ریپو دسترسی ندارند.

**در همه‌ی پرامپت‌ها فایل [`docs/DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md) را هم paste کن.**
بدون آن هر مدل رنگ و اندازه‌ی خودش را می‌سازد و «سبک یکی» اتفاق نمی‌افتد.

ترتیب پیشنهادی: ۱ → ۲ → ۳ → ۴. تسک ۱ و ۴ به بقیه وابسته نیستند و می‌توانند موازی بروند.

## قرارداد API (مشترک بین همه‌ی پرامپت‌ها)

این بخش را داخل هر پرامپتی که با سرور کار دارد paste کن.

```
همه‌ی درخواست‌ها هدر دارند:  Authorization: Bearer <token>
ورود:  POST /auth/login {username, password} → { access_token }
آدرس پایه در محیط توسعه:  http://127.0.0.1:3000

--- کالا و موجودی ---
GET  /products/search?q=<متن>
GET  /inventory/product/:productId/stock
     → [{ locationId, locationName, locationCode, locationBarcode, locationPath, quantity }]
       فقط مکان‌هایی که موجودی مثبت دارند.
GET  /inventory/sale/resolve/:barcode
     → { product:{id,name,sku,unit,salePrice}, stock:[ همان ساختار بالا ] }

--- فاکتور فروش ---
POST /sales/invoices
{
  "idempotencyKey": "<uuid تولید کلاینت>",
  "warehouseId": "...",
  "customerId": "..." | null,
  "customer": { "firstName":"...", "lastName":"...", "phone":"..." } | null,
  "discount": 5000,
  "note": "...",
  "lines": [ { "productId":"", "locationId":"", "quantity":2, "unitPrice":150000, "discount":0 } ],
  "payments": [
    { "method":"CASH|CARD|CHEQUE|CREDIT", "amount":100000, "note":"",
      "cheque": { "number":"", "bankName":"", "branch":"", "holderName":"", "dueDate":"2026-09-01" } }
  ]
}
پاسخ: فاکتور کامل با number, subtotal, discount, total, paidAmount, dueAmount,
profit, status, customer, payments[{...cheque}],
lines[{ quantity, unitPrice, product:{id,name,sku,unit}, location:{id,name,code,path} }]

نکته‌ها:
- اگر payments نفرستی، یعنی کل مبلغ نقد دریافت شده.
- CREDIT یعنی نسیه: در paidAmount حساب نمی‌شود و مشتری الزامی است.
- یک کالا از یک مکان نباید دو ردیف جدا داشته باشد — کلاینت باید ادغام کند.

خطاها:
409 { error:"INSUFFICIENT_STOCK", lineIndex, productId, locationId, requested, available, message }
400 { error:"DUPLICATE_LINE" | "DISCOUNT_EXCEEDS_TOTAL" | "OVERPAYMENT"
       | "CUSTOMER_REQUIRED_FOR_CREDIT" | "CHEQUE_DETAILS_REQUIRED" | "NAME_REQUIRED", message }

GET  /sales/invoices?warehouseId=&customerId=&q=&status=&from=&to=&page=&pageSize=
     → { data:[...], meta:{ total, page, pageSize, pageCount } }
GET  /sales/invoices/:id
POST /sales/invoices/:id/cancel   { "reason":"..." }     (فقط مدیر)

--- مشتری ---
GET    /sales/customers?q=&page=&pageSize=
       q روی نام، فامیل و شماره‌ی ناقص کار می‌کند.
       → { data:[{ id, firstName, lastName, fullName, phones:[{id,phone,label,isPrimary}] }], meta }
GET    /sales/customers/:id
       → + invoices[] + summary:{ totalPurchased, totalDue }
POST   /sales/customers   { firstName, lastName?, note?, smsOptOut?, phones?:[{phone,label?,isPrimary?}] }
       فقط firstName الزامی است — ثبت مشتری بدون شماره باید ممکن باشد.
PATCH  /sales/customers/:id
POST   /sales/customers/:id/phones          { phone, label?, isPrimary? }
DELETE /sales/customers/:id/phones/:phoneId

--- ارسال لوکیشن به کارگر ---
POST /pick-tasks
{ "warehouseId":"", "invoiceId":null,
  "lines":[ { "productId":"", "locationId":"", "quantity":2, "note":"" } ] }
GET  /pick-tasks?status=PENDING&warehouseId=
GET  /pick-tasks/mine        (صف کارگر)
POST /pick-tasks/:id/picked  (کارگر: «آوردم»)
POST /pick-tasks/:id/cancel  { "reason":"" }
وضعیت‌ها: PENDING | PICKED | CANCELLED
```

## تسک ۱ — قاب دسکتاپ Tauri

**فایل‌های همراه:** `apps/web/package.json`، `apps/web/next.config.*`، `DESIGN_SYSTEM.md`

```
تو یک مهندس ارشد دسکتاپ هستی. Tauri v2 + Rust + Next.js.

یک پروژه‌ی Tauri بساز که اپ Next.js موجود ما را در قاب دسکتاپ ویندوز اجرا کند.
اپ وب را بازنویسی نکن — فقط قابش را بساز.

الزامات:
- خروجی یک فایل نصب ویندوز (.msi یا .exe).
- در حالت توسعه به http://localhost:3001 وصل شود؛ در حالت تولید به آدرس سرور
  on-prem که کاربر بتواند در صفحه‌ی تنظیمات عوضش کند (سرور روی شبکه‌ی داخلی است،
  نه اینترنت). آدرس در فایل تنظیمات کنار برنامه ذخیره شود.
- پنجره: حداقل ۱۲۸۰×۸۰۰، قابل تمام‌صفحه، عنوان فارسی.
- منوی برنامه حذف یا حداقلی باشد (کاربر فروشنده است، نه توسعه‌دهنده).
- کلید F11 تمام‌صفحه، Ctrl+R بارگذاری مجدد.
- دستور Rust با نام `print_receipt` که یک رشته‌ی بایت ESC/POS می‌گیرد و به
  پرینتر پیش‌فرض ویندوز می‌فرستد. اگر پرینتر نبود، خطای فارسی روشن برگرداند.
  فعلاً فقط امضای دستور و مسیر خطا را کامل کن.
- دستور Rust با نام `list_printers` که فهرست پرینترهای نصب‌شده را برگرداند.

خروجی: ساختار کامل پوشه، Cargo.toml، tauri.conf.json، کد Rust، و دستورهای
build. مرحله‌به‌مرحله بگو چطور اجرا و بیلد کنم.
```

## تسک ۲ — صفحه‌ی فروش (POS) — بزرگ‌ترین کار

**فایل‌های همراه:** قرارداد API بالا، `DESIGN_SYSTEM.md`،
`apps/web/src/app/admin/review/page.tsx` (برای سبک)، `apps/web/src/lib/api.ts`

```
تو یک توسعه‌دهنده‌ی ارشد فرانت‌اند هستی. Next.js App Router + TypeScript +
shadcn/ui + react-query. دقیقاً از سبک فایل review/page.tsx که پیوست کردم پیروی کن.

صفحه‌ی /admin/pos را بساز: صندوق فروش برای فروشنده روی ویندوز.

معیار اصلی سرعت است. باید بتوان یک فاکتور کامل را **بدون دست زدن به ماوس** بست.
سرعتش باید در حد نرم‌افزار هلو باشد.

ساختار صفحه:
- بالا: فیلد اسکن/جست‌وجوی کالا که همیشه فوکوس دارد. بارکدخوان USB خودش را
  کیبورد جا می‌زند، پس بعد از هر کار فوکوس باید به این فیلد برگردد.
- وسط: جدول ردیف‌های فاکتور. هر ردیف: نام کالا، مکان، تعداد، قیمت واحد،
  تخفیف ردیف، جمع. تعداد و قیمت درجا قابل ویرایش با کیبورد.
- راست: کارت مشتری. جست‌وجو با نام یا شماره؛ اگر نبود، ساخت مشتری فقط با
  نام و فامیل (شماره اختیاری). بعد از انتخاب: نام، شماره، و مانده‌ی بدهی نشان داده شود.
- پایین: جمع کل، تخفیف فاکتور، مبلغ نهایی، و دکمه‌های پرداخت و ثبت.

رفتار کیبورد (این مهم‌ترین بخش کار است):
- F2 ثبت فاکتور · F3 جست‌وجوی کالا · F4 مشتری · F6 تخفیف · F7 پرداخت
  · F9 ارسال لوکیشن به کارگر · Esc بستن پنجره · Enter تأیید ردیف و برگشت به اسکن
- بالا/پایین بین ردیف‌ها، Delete حذف ردیف.
- میانبر روی خود دکمه نوشته شود، مثلاً «ثبت فاکتور F2».

منطق:
- اسکن بارکد → GET /inventory/sale/resolve/:barcode. اگر کالا در چند مکان
  موجودی داشت، فهرست مکان‌ها با موجودی نشان داده شود تا فروشنده انتخاب کند.
  اگر فقط یک مکان بود، خودکار انتخاب شود.
- اسکن دوباره‌ی همان کالا از همان مکان → تعداد ردیف موجود زیاد شود، ردیف جدید ساخته نشود.
  (سرور ردیف تکراری را رد می‌کند.)
- پرداخت: پنجره‌ای که چند سطر پرداخت می‌پذیرد (نقد / کارت / چک / نسیه).
  جمع پرداخت‌ها و مانده زنده محاسبه شود. برای چک، فیلدهای شماره، بانک و
  تاریخ سررسید شمسی. برای نسیه، مشتری الزامی است.
- ثبت: idempotencyKey با crypto.randomUUID تولید شود و **تا موفق شدن یا خطای
  قطعی عوض نشود** — اگر شبکه قطع شد و کاربر دوباره زد، نباید فاکتور تکراری بسازد.
- خطای 409 INSUFFICIENT_STOCK: با lineIndex همان ردیف را قرمز کن و موجودی
  واقعی را کنارش بنویس. کل فاکتور را دور نریز.
- F9: ردیف‌های انتخاب‌شده را با POST /pick-tasks برای کارگر بفرست و تأیید نشان بده.

قوانین سخت:
- تمام متن‌ها فارسی، RTL کامل.
- مبالغ به **تومان**، با ارقام فارسی و جداکننده‌ی هزارگان. ورودی هم فارسی هم
  انگلیسی قبول شود. هیچ‌جا «ریال» ننویس.
- اعداد جدول با font-variant-numeric: tabular-nums تا ستون‌ها نلرزند.
- فقط رنگ‌ها و اندازه‌های DESIGN_SYSTEM.md. هیچ رنگ یا اندازه‌ی جدیدی نساز.
- انیمیشن حداکثر ۱۵۰ms.
- هیچ کتابخانه‌ی جدیدی اضافه نکن.

خروجی: کد کامل و قابل اجرا، به فایل‌های منطقی تقسیم‌شده.
```

## تسک ۳ — گزارش‌ها

**فایل‌های همراه:** قرارداد API، `DESIGN_SYSTEM.md`، `apps/web/src/lib/api.ts`

```
Next.js App Router + TypeScript + shadcn/ui + react-query.

صفحه‌ی /admin/reports را با این گزارش‌ها بساز (هر کدام یک تب):
۱. فروش دوره‌ای — مبلغ کل، تعداد فاکتور، میانگین فاکتور، نمودار ستونی روزانه
۲. سود دوره‌ای
۳. بدهکاران — مانده‌ی نسیه هر مشتری، مرتب نزولی
۴. چک‌ها — سررسید نزدیک / وصول‌شده / برگشتی
۵. پرفروش‌ها و راکدها
۶. موجودی زیر حد
۷. عملکرد فروشنده

قواعد (این‌ها گزارش را «قوی» می‌کنند):
- بازه‌ی پیش‌فرض «امروز» + دکمه‌های یک‌کلیکی: دیروز، این هفته، این ماه، ماه گذشته.
  کاربر برای گزارش روزانه نباید تاریخ انتخاب کند.
- هر عدد قابل کلیک باشد و ردیف‌های زیرینش را در یک کشو باز کند.
- ردیف جمع همیشه دیده شود (چسبیده به پایین جدول، نه انتهای اسکرول).
- دکمه‌ی خروجی اکسل روی هر گزارش.
- صفحه‌بندی سمت سرور — هیچ گزارشی همه‌ی ردیف‌ها را نکشد.
- حالت خالی معنادار: «در این بازه فروشی ثبت نشده» + دکمه‌ی تغییر بازه.
- تاریخ شمسی، مبالغ تومان با ارقام فارسی و tabular.

اگر endpoint گزارشی در قرارداد نبود، فرض کن وجود دارد، شکل درخواست و پاسخی که
لازم داری را **صریح مستند کن**، و UI را رویش بساز. آن endpointها بعداً ساخته می‌شوند.
هیچ کتابخانه‌ی جدیدی اضافه نکن (برای نمودار از recharts که در shadcn هست استفاده کن).
```

## تسک ۴ — قالب چاپ فیش و فاکتور

**فایل‌های همراه:** `apps/api/src/labels/label-template.ts` (برای سبک)، `DESIGN_SYSTEM.md`

```
TypeScript، بدون فریم‌ورک.

دو قالب چاپ برای فاکتور فروش فارسی بنویس. هر کدام یک تابع که داده می‌گیرد و
رشته برمی‌گرداند.

الف) فیش حرارتی ۸۰ میلی‌متری — خروجی ESC/POS
- سربرگ: نام فروشگاه، شماره فاکتور، تاریخ و ساعت شمسی
- نام مشتری اگر باشد
- ردیف‌ها: نام کالا (در صورت بلندی بشکند)، تعداد × قیمت، جمع ردیف
- جمع کل، تخفیف، مبلغ نهایی، نوع پرداخت
- پاورقی: تشکر + شماره تماس فروشگاه
- برش کاغذ در انتها

ب) فاکتور A5 و A4 — خروجی HTML
- همان اطلاعات با جدول کامل و ستون ردیف
- مبلغ کل به عدد و به حروف فارسی
- جای امضای فروشنده و خریدار
- CSS مخصوص چاپ (@media print)، بدون هیچ فایل خارجی — فونت و CSS همه inline

قوانین:
- RTL، ارقام فارسی، مبالغ به تومان با جداکننده‌ی هزارگان. هیچ‌جا «ریال» ننویس.
- تابع تبدیل عدد به حروف فارسی را هم بنویس (مثلاً ۱۲۵۰۰۰ → «صد و بیست و پنج هزار تومان»).
- برای فیش حرارتی، عرض ثابت ۴۸ کاراکتر را رعایت کن و متن فارسی را درست بشکن.
```
