# نقشه راه اجرایی — «سند خودکار + UX بدون آموزش»

**تاریخ:** ۱۴۰۵/۰۶/۱۱ · وضعیت: نقشهٔ نهایی کار · پیش‌نیاز مفهومی: `docs/AUTO_VOUCHER_PLAIN_UX.md`
**اصل ثابت همهٔ فازها:** هر اکشن در همان تراکنش دیتابیس سند خودش را میگیرد؛ سند append-only است
(اصلاح = سند معکوس)؛ واحد مبالغ **ریال** است؛ UI هیچ اصطلاح حسابداری نشان نمیدهد (لغت‌نامه واحد: بدهکار → «بدهی مشتری»…).

> کشف مهم از بررسی اسکیما: **نیمی از زیرساخت از قبل هست** — `CustomerLedger` (append-only با
> قرارداد «مثبت = بدهی بیشتر» و مانده = SUM)، `ReceiptAllocation` (تخصیص FIFO به فاکتورها!)،
> `PaymentReversal` (سند خنثیساز پرداخت)، `SaleReturn/SaleCorrection` (سند مرجوعی/اصلاحیه).
> یعنی فاز ۱ «ساخت از صفر» نیست؛ «ساخت لایهٔ دوبلانتری روی این اسکلت سالم» است.

## فاز ۱ — هستهٔ سند خودکار (قلب کار) 🔴 — ✅ هسته و پستینگ انجام شد (۱۴۰۵/۰۶/۱۳)

  `reversesVoucherId` (سند معکوس) و `idempotencyKey` یکتا. ۱۱ حساب ثابت سیستمی
  (صندوق، بانک، چک، مشتریان، بازپرداخت مشتری، تأمینکنندگان، فروش، برگشت فروش، تخفیف،
  موجودی، بهای تمامشده، درآمد فروش مدت).
- [x] `PostingService.post(tx, ...)` — موازنه اجباری (جمع خطوط = صفر، وگرنه کل اکشن میشکند)
  + idempotency (کلید تکراری سندِ دوباره نمیسازد) + `latestPurchasePrices` برای COGS.
- [x] پستینگ رویدادهای زنده، همه داخل همان تراکنش مبدأ: فاکتور فروش (نقد/چک/نسیه + تخفیف +

  ابطال فروش (سند معکوس؛ وجهِ گرفتهشده بستانکارِ «بازپرداخت مشتری» میشود تا سند موازنه
  بماند — بازپرداختِ واقعی در فاز ۲ از همین حساب صاف میشود)، خرید و ابطال خرید
  (موجودی در برابر تأمینکنندگان).
- [x] Backfill منتفی شد (تصمیم کاربر: نقطهٔ شروع پاک، بدون backfill حدسی — در NEXT_TASK ثبت شده).
- [x] API دفتر روزنامه: `GET /vouchers` (لیست+فیلتر)، `GET /vouchers/source/:type/:id` (لینک «چی به چی»)،
  `GET /vouchers/:id` — فقط ADMIN/MANAGER.
- [x] صفحهٔ UI دفتر روزنامه (`/admin/vouchers`): فیلتر نوع/بازهٔ تاریخ، ردیف‌های بدهکار/بستانکار با
  برچسب فارسی، نشانِ تراز، لینک به سندِ مبدأ (فاکتور/رسید/خرید)، صفحه‌بندی — تأیید زنده در مرورگر.
  (برای پیش‌نمایش محلی، `127.0.0.1` به `allowedDevOrigins` در `next.config.ts` اضافه شد.)
- [x] رفت‌وبرگشتِ عمیق سند ↔ فاکتور: هر سندِ مرجوعی/اصلاحیه لینک «مشاهدهٔ فاکتور مبدأ» دارد
  (فاکتورِ مبدأ روی سرور با دو کوئریِ دسته‌ای حل و در `invoiceId` برگردانده میشود)؛
  `GET /vouchers/by-invoice/:id` همهٔ سندهای یک فاکتور را به ترتیبِ زمان میدهد (فروش، ابطال،
  رسیدهای تخصیص‌یافته، مرجوعی‌ها، اصلاحیه‌ها)؛ کارتِ مشترک `VoucherCard` در دفتر روزنامه و
  بخشِ «سندهای خودکار این فاکتور» در صفحهٔ فاکتور — تأیید زندهٔ رفت‌وبرگشت با مرجوعی و
  اصلاحیهٔ واقعی روی فاکتور ۳۱.
- [x] تأیید زنده روی دیتابیس واقعی: فروش ۱۰۰میلیون (۶۰ نقد + ۴۰ نسیه) → سند متوازن؛
  رسید ۴۰ → سند متوازن؛ ابطالِ فاکتورِ کاملاً تسویهشده → سندِ معکوس متوازن با لینک به
  سندِ اصلی؛ ماندهٔ مشتری دقیقاً به حالت قبل برگشت. ۲۵۴ تست پاس.
**پذیرش:** هر سند جدید بدهکار=بستانکار (تست زنده انجام شد) · از هر عدد به فاکتور مبدأ و برعکس رفتنی است (`/vouchers/source/...`).

## فاز ۲ — پستینگ کامل رویدادهای پولی + «چی به چی» 🟠 — ✅ کامل شد (۱۴۰۵/۰۶/۱۴)
- [x] **تستِ تطبیقِ سندری** (`ReconciliationService` + `GET /vouchers/reconcile` + ۵ تست API):
  ماندهٔ هر حسابِ ثابت از سندها با ماندهٔ مدلِ عملیاتی مقایسه می‌شود و در تست‌های API سبز می‌ماند —
  CUSTOMERS از دفترِ مشتری (به‌تفکیکِ مشتری؛ ردیف‌های دستیِ OPENING/ADJUSTMENT عمداً مستثنا)،
  SUPPLIERS از فاکتورهای خرید (confirmed − cancelled)، CHEQUES از چک‌هایِ دستِ‌ما (IN_HAND) منهای
  چکِ پرداختی به مشتری، و SALES/DISCOUNT/FINANCE_CHARGE/SALES_RETURN از خودِ فاکتورها و
  مرجوعی‌ها و اصلاحیه‌ها. CASH/BANK/REFUND_PAYABLE/INVENTORY/COGS مدلِ عملیاتیِ مستقل ندارند و
  informational گزارش می‌شوند؛ به‌جایشان «پوششِ سند» (هر سندِ عملیاتی، سندِ مالی‌اش را دارد) و
  «موازنهٔ همیشگیِ سندها» چک می‌شود.
  تست‌ها: سناریوی کاملِ دخل (فروش نقد/نسیه/چک، رسید، مرجوعیِ نقدی و نسیه‌ای، اصلاحیه، چرخهٔ چک،
  پرداخت به مشتری، خرید) → سبز؛ اختلافِ پستینگ و سندِ گم‌شده → قرمز با ردیفِ دقیقِ اختلاف.
  روی دیتابیس واقعیِ فعلی قرمز می‌ماند — عمدی: تاریخچهٔ پیش از دورانِ سند، سند ندارد (بدون backfill،
  طبق تصمیمِ «نقطهٔ شروع پاک»)؛ روی شروعِ پاک و در تست‌های API سبز است. ۲۶۳ تست پاس.
- [ ] (باقی‌مانده) گزارشِ UI «گردشِ هر حساب/چک» به سبک پارسیان (موجودیِ بانک + چکِ فعال) و گسترش
  `ChequeStatus` با سرحساب/واگذاری/عودت — یک گزارشِ نمایشی روی همین ReconciliationService.
- [x] `CustomerPayout`، `PaymentReversal` → سند خودشان؛ و صاف‌کردنِ حسابِ «بازپرداخت مشتری»
  (سندِ ابطال وجه را آنجا بستانکار کرده؛ بازپرداختِ واقعی باید همان را بدهکار کند).
**پذیرش:** تستِ تطبیق در تست‌های API سبز؛ «گردش چک‌ها» پارسیانی (موجودی بانک + چک فعال) بعداً گزارش شود.

## فاز ۳ — POS: برگشت در همان سبد + زبان ساده 🟠
- [x] **هستهٔ سبدِ خالص (بک‌اند) — کامل شد:** ردیف‌هایِ مرجوعیِ چند فاکتورِ
  قبلیِ همین مشتری + فروشِ نو در **یک درخواستِ اتمیک** (`POST /sales/net`).
- [x] **دیالوگِ تعویض (F10) — کامل شد (۱۴۰۵/۰۶/۱۴):** همان سبدِ دوگانه در یک پنل:
  ردیف‌هایِ برگشت (قرمز؛ قیمت از فاکتورِ مبدأ، سقفِ قابل‌برگشت، سالم/معیوب) کنارِ
  ردیف‌هایِ فروشِ نو (افزودن با بارکد/نام، قیمتِ آموخته‌شده) با **جمعِ زنده**:
  «جمعِ نو − برگشت = قابل دریافت»؛ خالصِ منفی با پیامِ ساده رد و ثبت غیرفعال
  می‌شود. دلیل از چیپ‌های آماده (تعویض جنس/معیوب/اشتباه)؛ فرمان فقط روی فروشِ
  عادیِ دارایِ مشتری فعال است. تأییدِ زنده در مرورگر: فاکتور ۴۴ + مرجوعی ۲۷ با
  سندهایِ موازنه (فروش + برگشت).
- [ ] (بعداً) ادغامِ همان ردیف‌هایِ قرمز در جدولِ اصلیِ تب — دیالوگ امروز جدا و
  تست‌پذیر است و الگویِ ادغام را نشان می‌دهد.
- [ ] خلاصهٔ قبل از ثبت به زبان ساده برای بقیهٔ مسیرها + Undo حذف ردیف (B2 بکلاگ)
  + لغت‌نامهٔ واحد اصطلاحات در همهٔ لیبل‌ها.
**پذیرش:** سناریوی «۱۰ لنت + ۵۰ چراغ + ۲۰ سپر − چند برگشت + دوباره برداشت» در یک نشست، بدون موس، بدون یک اصطلاح حسابداری.

## فاز ۳٫۵ — «اصلاح نحوهٔ پرداخت» فاکتورِ ثبت‌شده ✅ کامل شد (۱۴۰۵/۰۶/۲۱)

سناریو: فاکتورِ ۱۰۰ میلیونی همه‌اش کارتخوان زده شده، ولی واقعیت ۳۰ نقد و ۷۰ نسیه
بوده. پیش از این هیچ مسیری این را نمی‌پذیرفت: نه اصلاحیه (تغییرِ صفر رد می‌شد) و نه
تسویهٔ اختلاف (اختلافی وجود نداشت).

- [x] **`GET /sales/invoices/:id/settlement`** — تقسیمِ خالصِ هر روش + `canRecompose`
  با `blockedReason` فارسی: باطل / چکدار / پولش از رسید خورده / فروشنده روی گذشته.
- [x] **`POST /sales/invoices/:id/recompose-payments`** — **نوشتنِ تفاضلی** به‌ازای هر
  روش، در یک تراکنش با قفلِ فاکتور: ردیفِ منفیِ «برداشت» + ردیف‌های تازه؛ هیچ ردیفی
  حذف نمی‌شود. یک کلیدِ عملیات روی همه می‌نشیند، پس retryِ شبکه ردیفِ تکراری نمی‌سازد.
- [x] **سند و دفترِ خودکار** — یک `LedgerEntry` از نوع `RECOMPOSE` و یک voucher از نوع
  `PAYMENT_RECOMPOSE` (مشتریان + / صندوق −). اگر تقسیم فقط جای نقد و کارت را عوض کند،
  پولی جابه‌جا نشده و سندی ساخته نمی‌شود.
- [x] **فاکتورِ بی‌مشتری** با نسیه‌کردن مشتری می‌گیرد و سررسید از اعتبارِ او می‌آید.
- [x] **UI** — پنلِ «اصلاح نحوهٔ پرداخت» (نقد/کارتِ قابل‌تایپ + نسیهٔ محاسبه‌شده)،
  روشن‌شدنِ F2 در ویرایشِ بی‌تغییر، کلید P در پنلِ فاکتورهای مشتری، برچسبِ «برداشت»
  برای ردیف‌های منفی در صفحهٔ فاکتور و روی برگهٔ چاپی، و برچسبِ فارسیِ `RECOMPOSE`
  در صورت‌حساب و دفتر.
- [x] **۱۶ تستِ API** برای همین سرویس (تفاضل، idempotency، چک، رسید، دسترسی، ردها).

## اولویتبندی و توالی
فاز ۰ → ۱ (بلافاصله، پشت هم) · فاز ۲ و ۳ موازی قابل تقسیم (۲ بکاند، ۳ فرانت) → ۴ → ۵.
با تصمیم فعلی، راه‌اندازی با **نقطهٔ شروع پاک** انجام میشود و تاریخچهٔ قدیمی فقط بعد از ممیزی جداگانه بررسی میشود.

## ریسکها
1. **Backfill آلوده** — اگر فاز ۰ انجام نشود، سندهای تاریخی COGS غلط میشوند → فاز ۰ اجباری است.
2. **پستینگ دوباره** — idempotencyKey روی Voucher (الگوی موجود SaleInvoice/Receipt).
3. **دو مرجع مانده** — قانون: ماندهٔ نمایشی همیشه از CustomerLedger، سند فقط پشت صحنه؛ تست تطبیق فاز ۲ باید همیشه سبز بماند.
4. **بهرهبرداری بدون آموزش** — هر فاز با یک سناریوی دخل واقعی پذیرفته میشود؛ معیار: «فرد بیسواد مالی».
