# نصب روی ویندوز

## ⚠️ قانون اسکریپت‌ها: فقط ASCII

`build.ps1`، `first-run.ps1`، `services.ps1` و `installer.iss` **نباید هیچ بایت
غیر‌ASCII داشته باشند** — نه کامنت فارسی، نه پیام فارسی، نه «…» و نه خط تیره‌ی
بلند.

دلیلش این نیست که فارسی بد است؛ این است که Windows PowerShell 5.1 فایل `.ps1` را
با codepage محلی ویندوز می‌خواند نه UTF-8. هر بایت غیر‌ASCII خراب می‌شود و همان
بایت خراب پارسر را می‌شکند — یعنی اسکریپت روی **سیستم مشتری** اجرا نمی‌شود، نه
اینجا. Inno Setup هم بدون BOM دقیقاً همین رفتار را دارد و اسم میان‌برها را
به‌هم‌ریخته نشان می‌دهد.

BOM هم جواب می‌دهد ولی شکننده است: هر ویرایشگری که BOM را بردارد دوباره
می‌شکند، آن هم بی‌صدا.

رشته‌های فارسی‌ای که **مشتری می‌بیند** (اسم میان‌برها) در `first-run.ps1` از روی
code point ساخته می‌شوند. فارسی فقط در همین `README.md` می‌ماند، چون هیچ‌چیز
آن را پارس نمی‌کند.

بررسی قبل از کامیت:

```bash
LC_ALL=C grep -n '[^[:print:][:space:]]' deploy/windows/*.ps1 deploy/windows/*.iss
```

خروجی باید خالی باشد.

## چرا باید روی ویندوز build شود

`sharp`، `argon2` و موتور کوئری پریزما باینریِ مخصوص سیستم‌عامل‌اند. `npm install`
روی مک باینری مک تولید می‌کند و روی سرور ویندوز اجرا نمی‌شود. پس **بسته باید روی
همان لپ‌تاپ ویندوزی ساخته شود**، نه روی مک.

## یک بار: چیزهایی که لازم است

| | از کجا |
|---|---|
| Node.js **24** — **ZIP** نه MSI | nodejs.org/en/download |
| PostgreSQL **18** — **Binary ZIP** نه Installer | enterprisedb.com/download-postgresql-binaries |
| Inno Setup | jrsoftware.org/isdl.php |
| NSSM 2.24 | nssm.cc/download |

نسخه‌ها باید **همان‌هایی باشند که توسعه با آن‌ها انجام شده** (Node 24، Postgres 18)،
نه قدیمی‌تر:

- دامپ `pg_dump -Fc` از پستگرس ۱۸ در نسخه‌ی ۱۶ **قابل بازیابی نیست**. با نسخه‌ی
  متفاوت، انتقال داده بین محیط توسعه و سرور مشتری یک‌طرفه می‌شود.
- باینری‌های بومی (sharp، argon2، پریزما) به ABI نود گره خورده‌اند.

`build.ps1` **هر دو** را بررسی می‌کند — نسخه‌ی Node روی PATH، نسخه‌ی Node داخل
ZIP، و major پستگرس — و اگر یکی نخواند همان‌جا شکست می‌خورد. چون آن خطا در غیر
این صورت سرِ مشتری ظاهر می‌شود، نه موقع ساخت.

ویندوز ۷ فروشنده هیچ ربطی به این نسخه‌ها ندارد: آنجا نه Node اجرا می‌شود نه
Postgres، فقط کروم.

Node را روی خود لپ‌تاپ هم نصب کن (یا به PATH اضافه‌اش کن) — برای اجرای build لازم است.

## ساخت بسته

```powershell
cd deploy\windows
.\build.ps1 -NodeZip C:\dl\node.zip -PgZip C:\dl\pg.zip -NssmZip C:\dl\nssm.zip
```

بعد `installer.iss` را با Inno Setup باز کن و Compile بزن. خروجی:
`Output\WarehouseOS-Setup-0.2.0.exe`

دو نکته که `build.ps1` خودش حل می‌کند و اگر دستی کار کردی باید حواست باشد:

- **CLI پریزما** در `package.json` اپ نیست (devDependency ریشه است)، پس
  `npm install --omit=dev` نمی‌آوردش. بدون آن `migrate deploy` سرِ مشتری اجرا
  نمی‌شود. build همان نسخه‌ای را که ریشه نصب کرده داخل بسته می‌گذارد و وجود
  فایلش را چک می‌کند.
- **خروجی standalone نکست** ساختار پوشه‌ی ماشین build را آینه می‌کند و
  `node_modules` را در بیش از یک سطح آن پخش می‌کند — خودِ `next` در سطح داخلی
  است. کل درخت کپی می‌شود و یک `server.js` واسط در مسیر ثابت ساخته می‌شود تا
  سرویس همیشه یک مسیر مشخص برای اجرا داشته باشد.

## نصب روی سرور مشتری

`Setup.exe` را **به‌عنوان مدیر** اجرا کن. خودش:

دیتابیس می‌سازد · رمزها را تولید می‌کند · مهاجرت‌ها را اجرا می‌کند · پوشه‌ی
بکاپ را تثبیت می‌کند · سه سرویس ثبت می‌کند · پورت‌ها را روی شبکه‌ی محلی باز
می‌کند · میان‌بر می‌سازد · و آخرش **بررسی می‌کند که هر دو سرویس واقعاً جواب
می‌دهند**.

اگر جواب ندادند، صریح می‌گوید کدام و لاگش کجاست.

پنجره‌ی نصب با بسته شدن نصب‌کننده می‌رود، پس همه‌چیز در دو جا می‌ماند:

- `INSTALL-INFO.txt` در ریشه‌ی نصب — آدرس سرور، محل رمز مدیر، کارهای بعدی.
  نصب‌کننده خودش بازش می‌کند.
- `data\install.log` — رونوشت کامل اجرا، برای وقتی چیزی خراب شده.

## چیدمان پوشه‌ها

```
C:\WarehouseOS\
  app\        کد و رانتایم — با هر آپدیت عوض می‌شود
  pgsql\      باینری‌های پستگرس (pg_dump هم همین‌جاست)
  data\       دیتابیس و لاگ‌ها — هرگز دست نمی‌خورد
  config\     .env با رمزها — هرگز دست نمی‌خورد
  backups\    دامپ‌های شبانه
  versions\   نسخه‌ی قبلی برای برگشت
  INSTALL-INFO.txt
```

هرچه مالِ مشتری است بیرون از `app` می‌ماند. این تنها چیزی است که آپدیت را
بی‌خطر می‌کند و بعداً قابل تغییر نیست. حذف برنامه هم `data`، `config`،
`backups` و `versions` را دست نمی‌زند — عمدی است.

## تنظیمات

`config\.env` با ASCII نوشته می‌شود، **نه** با `-Encoding utf8`. در PowerShell 5.1
معنی `utf8` یعنی «UTF-8 با BOM»، و آن سه بایت به اسم اولین کلید می‌چسبند:
`DATABASE_URL` بی‌صدا گم می‌شود و API بالا نمی‌آید.

مسیرها بدون کوتیشن نوشته می‌شوند تا بک‌اسلش به‌عنوان escape خوانده نشود.

## سرویس‌ها

`WarehouseOS-DB` → `WarehouseOS-API` → `WarehouseOS-Web`، با همین ترتیب وابستگی
تا بعد از قطع برق درست بالا بیایند. لاگ‌ها در `data\*.log` با چرخش ۱۰ مگابایتی.

### چرا سرویس دیتابیس با NetworkService اجرا می‌شود

**پستگرس روی ویندوز زیر یک حساب مدیر بالا نمی‌آید.** در سورس خودش
(`check_root()` در `main.c`) اگر `pgwin32_is_admin()` درست باشد با این پیام
خارج می‌شود:

> Execution of PostgreSQL by a user with administrative permissions is not permitted.

حساب پیش‌فرض سرویس در NSSM «LocalSystem» است که **عضو Administrators است** —
یعنی سرویس دیتابیس تمیز ثبت می‌شد و بعد هیچ‌وقت بالا نمی‌آمد. به همین دلیل
`WarehouseOS-DB` با `NT AUTHORITY\NetworkService` اجرا می‌شود: حساب داخلیِ
کم‌دسترسی، نه در Administrators نه در Power Users، و رمزی هم ندارد که جایی
ذخیره شود.

دو نتیجه‌ی مستقیم:

- پوشه‌ی `data` با `icacls` به همان حساب داده می‌شود (با SID `*S-1-5-20`، نه با
  اسم — اسم روی ویندوز غیرانگلیسی ترجمه می‌شود و پیدا نمی‌شود). بدون این،
  سرویس یک بایت هم نمی‌تواند بنویسد.
- `first-run.ps1` دیگر پستگرس را موقتاً با `pg_ctl` بالا نمی‌آورد؛ چون خودش
  elevated است و دقیقاً به همان منع می‌خورد. به‌جایش همان سرویس واقعی را
  زودتر ثبت و روشن می‌کند (`services.ps1 -DbOnly`) و مهاجرت‌ها را روی آن اجرا
  می‌کند. یعنی دیتابیس از همان لحظه‌ی نصب دقیقاً همان‌طوری بالا می‌آید که هر
  روز صبح بالا خواهد آمد.

`initdb.exe` این محدودیت را ندارد (بررسی‌اش `#ifndef WIN32` است) و elevated
اجرا می‌شود.

`services.ps1` قبل از ثبت، وجود هر فایلی را که سرویس به آن اشاره می‌کند بررسی
می‌کند — وگرنه سرویس ثبت می‌شود و فقط موقع بوت شکست می‌خورد.

پورت API از `PORT` خوانده می‌شود (سرویس ست می‌کند) و روی همه‌ی اینترفیس‌ها گوش
می‌دهد، نه فقط لوکال — گوشی‌ها و سیستم فروشنده از شبکه وصل می‌شوند.

## بکاپ

مهم‌ترین چیزی است که تحویل می‌دهی. انباری که دفتر موجودی‌اش را از دست بدهد
می‌ایستد.

- شبانه ساعت ۲۳:۰۰، ۱۴ نسخه نگه داشته می‌شود، خودکار. مقصد در نصب روی
  `C:\WarehouseOS\backups` تثبیت می‌شود.
- `PG_DUMP_PATH` و `PG_RESTORE_PATH` در `.env` ست می‌شوند، چون `pg_dump` روی
  ویندوز روی PATH نیست. بدون آن‌ها بکاپ هر شب شکست می‌خورد و تنها نشانه‌اش یک
  خط در لاگ است.
- هر دامپ بعد از ساخته شدن **خوانده می‌شود** تا تأیید شود سالم است.

⚠️ **هنوز مانده:** بکاپ روی همان دیسکِ دیتابیس، بکاپ نیست. کپی شبانه روی درایو
دوم یا شبکه باید تنظیم شود، و **یک بار بازیابی واقعاً تست شود**. بکاپِ تست‌نشده
شایعه است.

## بعد از نصب

**۱. آی‌پی را روی روتر رزرو کن.** بدون این، فردا روتر عدد دیگری می‌دهد و گوشی‌ها
و سیستم فروشنده قطع می‌شوند.

**۲. سیستم فروشنده (ویندوز ۷):** فقط یک میان‌بر کروم لازم دارد، نه نصب:

```
"C:\Program Files\Google\Chrome\Application\chrome.exe" --app=http://192.168.2.100:3001/admin/pos
```

⚠️ آخرین کرومی که روی ویندوز ۷ اجرا می‌شود نسخه‌ی ۱۰۹ است. **قبل از تحویل حتماً
پنل را روی همان دستگاه باز کن.** اگر صفحه‌ی سفید داد، تارگت مرورگر باید روی
Chrome 109 پین شود و وب دوباره build شود.

**۳. گوشی کارگرها:** آدرس سرور را در تنظیمات اپ وارد کن.

**۴. رمز مدیر:** بار اول در `data\api.log` نوشته می‌شود و فقط یک بار نمایش
داده می‌شود. مسیرش در `INSTALL-INFO.txt` هم هست.

## آپدیت

اجرای دوباره‌ی `Setup.exe` روی نصب موجود بی‌خطر است: سرویس‌ها **قبل از کپی
فایل‌ها** متوقف می‌شوند (وگرنه فایل‌های قفل‌شده کپی نمی‌شوند) و `first-run.ps1`
وقتی `config\.env` را ببیند خودش رد می‌شود، پس دیتابیس و تنظیمات دست نمی‌خورند.

ولی مهاجرت‌ها را اجرا نمی‌کند. اگر نسخه‌ی جدید مهاجرت دارد:

```powershell
# ۱. اول بکاپ — بدون این راه برگشتی نیست
pgsql\bin\pg_dump.exe -h localhost -U postgres -Fc -f backups\pre-update.dump warehouse_os
# ۲. Setup.exe جدید را اجرا کن
# ۳. مهاجرت‌ها
app\node\node.exe app\api\node_modules\prisma\build\index.js migrate deploy
# ۴. سرویس‌ها را دوباره تعریف و روشن کن
scripts\services.ps1
```

**بکاپ قبل از هر آپدیت اجباری است.** برگشت به عقب هم پوشه‌ی قبلی را لازم دارد
هم دامپ را، چون ممکن است مهاجرت اجرا شده باشد.

⚠️ گرفتن بکاپ خودکار به‌عنوان قدم اول نصب‌کننده هنوز پیاده نشده.

## آنچه تست شده و آنچه نشده

**تست‌شده (روی مک):**

- هر چهار فایل بایت‌به‌بایت ASCII خالص‌اند، بدون BOM.
- ساختار اسکریپت‌ها: تعادل پرانتز و آکولاد، بسته‌بودن here-string‌ها و
  کامنت‌های بلوکی، و نبودِ نحو مخصوص PowerShell 7 (`??`، `&&`، ternary).
- قالب `.env` تولیدی با `process.loadEnvFile` نود ۲۴ خوانده می‌شود و مسیرهای
  ویندوزی سالم می‌مانند — و همان فایل با BOM، `DATABASE_URL` را گم می‌کند
  (تأیید شد).
- SQL تثبیت پوشه‌ی بکاپ روی اسکیمای واقعی اجرا شد (داخل تراکنش و rollback).
- خواندن `PORT` توسط API: با `PORT=3999` بالا آمد و روی `0.0.0.0:3999` جواب داد.
- منع اجرای پستگرس زیر حساب مدیر: از سورس پستگرس ۱۸ تأیید شد، نه از حافظه.

**تست‌نشده — این‌ها هنوز روی ویندوز اجرا نشده‌اند:**

- خودِ `build.ps1` و کامپایل Inno.
- `first-run.ps1` روی یک ویندوز تمیز: initdb، سرویس‌ها، فایروال، میان‌برها.
- پنل روی ویندوز ۷ با Chrome 109.
- چاپ روی پرینتر TSC واقعی.

توصیه: **اول روی خود لپ‌تاپ ویندوزی نصبش کن، نه مستقیم روی سرور مشتری.**

## انحراف‌های آگاهانه

- دیتابیس با کاربر `postgres` کار می‌کند، نه یک نقش کم‌دسترسیِ جدا. چون فقط روی
  localhost گوش می‌دهد و پورتش هرگز باز نمی‌شود، ریسکش پذیرفته شده — ولی درست
  نیست و باید بعداً جدا شود.
- ارتباط HTTP است نه HTTPS. روی شبکه‌ی محلیِ بسته پذیرفته شده؛ اگر شبکه بزرگ‌تر
  شد باید بازبینی شود.
- ویزارد نصب‌کننده انگلیسی است (Inno ترجمه‌ی فارسی رسمی ندارد). خودِ برنامه فارسی
  است و نصب را هم مجری انجام می‌دهد نه کارکنان انبار.
