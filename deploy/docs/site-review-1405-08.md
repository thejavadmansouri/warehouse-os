# بررسی فنی فروشگاه اینترنتی (`apps/site`)

تاریخ: آبان ۱۴۰۵ — نسخهٔ بررسی‌شده: همان HEAD مخزن

این سند فقط دربارهٔ اپِ `apps/site` است، نه پنل مدیریت (`apps/web`) و نه API.
هدف: گفتنِ «چه هست»، «چه خوب است»، «چه می‌شکند» و «با چه ترتیبی درست شود».

---

## ۱) تصویر کلی

| قلم | مقدار |
|---|---|
| فایل‌های TS/TSX | ۷۶ فایل، حدود ۷٬۲۰۰ خط |
| مسیرها (routes) | ۱۶ صفحه + دو route برای `robots.txt` و `sitemap.xml` |
| آزمون | ۱ فایل (`currency.test.ts`) |
| پورت توسعه | ۳۰۰۲ |
| حالت خروجی | `standalone`، تصاویر `unoptimized` |
| اتصال به API | `SITE_API_URL` (سمت سرور) و `NEXT_PUBLIC_SITE_API_PORT` (سمت کلاینت) |

مسیرها:

```
/                              → همان /shop
/shop                          کاتالوگ (کلاینتی) + متن سئوی سروررندر
/shop/product/[id]             صفحهٔ کالا (سئوی قوی)
/shop/cart  /shop/checkout     سبد و تسویه
/shop/account /shop/orders     حساب مشتری و سفارش‌ها
/shop/orders/[id]              جزئیات سفارش
/admin  /admin/login           ورود کارکنان
/admin/orders                  سفارش‌های فروشگاه
/admin/site/{banners,coupons,reviews,seo,shipping-zones,stock-notify}
```

این اپ یک **فروشگاه آمادهٔ استفاده برای یک مشتری واقعی** است (برند «شهر یدکی
صادقی»)، نه یک قالب خالی. یعنی الگوی کار درست است و برای مشتری بعدی باید
«چند-فروشگاهی» شود.

---

## ۲) چیزهایی که درست انجام شده

1. **سئوی صفحهٔ کالا، حرفه‌ای است.** `generateMetadata` عنوان، توضیح ۱۶۰
   کاراکتری، canonical، تصاویر و `AggregateRating` را از دادهٔ واقعی می‌سازد و
   JSON-LD محصول (`InStock` / `LimitedAvailability` / `OutOfStock`) تولید می‌کند
   (`src/app/shop/product/[id]/page.tsx`). این سطح، از اکثر فروشگاه‌های ایرانی
   بالاتر است.
2. **فیلترها در URL می‌نشینند** (`q`, `category`, `brand`, `vehicle`, `sort`,
   `page`, `inStock`, `minPrice`) — لینک قابل اشتراک، دکمهٔ Back سالم، و
   امکان ایندکس‌شدن صفحات فیلترشده.
3. **`robots.txt` و `sitemap.xml` از API پروکسی می‌شوند** و `base` را از
   `SITE_URL` می‌گیرند؛ یعنی سایت‌مپ با دامنهٔ درست ساخته می‌شود، نه با
   `localhost`. fallback هم دارد (سایت‌مپ خالی، نه ۵۰۰).
4. **تفکیک نشست مشتری از کارکنان.** توکن مشتری نوع `customer` دارد و در
   `localStorage` نگه داشته می‌شود؛ توکن کارکنان جای دیگری است. قاطی‌شدن این دو
   یک کلاس کامل از باگ‌های امنیتی است که اینجا پیشگیری شده.
5. **`rewrites` برای `/storage`** — تصاویر از همان مبدأ سرو می‌شوند؛ نتیجه:
   بدون خطای hydration `127.0.0.1` در برابر `localhost`.
6. **پرداخت در محل و کارت‌به‌کارت با منطقهٔ ارسال و کد تخفیف** کامل پیاده شده؛
   برای بازار ایران (که درگاه آنلاین برای همه مقدور نیست) انتخاب درستی است.

## ۳) یافته‌ها — به ترتیب اهمیت

### الف) این اپ بیرون از دروازهٔ کیفیت است (بالا)

شواهد:

- `apps/site/next.config.ts`: `typescript: { ignoreBuildErrors: true }` و
  `reactStrictMode: false`.
- `package.json` ریشه هیچ اسکریپتی برای سایت ندارد: نه `typecheck:site`، نه
  `test:site`، نه `build:site`.
- `.github/workflows/ci.yml` فقط `api` و `web` را بررسی می‌کند.

یعنی امروز می‌شود کدِ تایپ‌غلط را در سایت merge کرد و هیچ چیز قرمز نشود. با
توجه به این‌که سایت تنها جایی است که **مشتری نهایی** با آن کار می‌کند، این
بزرگ‌ترین شکاف است.

**اقدام:** افزودن `typecheck:site` / `test:site` / `build:site` به ریشه و یک
جابِ `site` به CI؛ بعد برداشتن `ignoreBuildErrors`. اگر برداشتنش الان خطا
می‌دهد، اول خطاها را بشمار و قدم‌به‌قدم ببند (مثل کاری که برای `web` شد).

### ب) هیچ مرز خطا و حالت بارگذاری ندارد (بالا)

هیچ `error.tsx`، `loading.tsx`، `not-found.tsx` یا `global-error.tsx` در
`src/app` وجود ندارد (بررسی شد). نتیجه:

- خطای یک کامپوننت = صفحهٔ سفیدِ کامل با پیام انگلیسیِ Next.
- کندی شبکه = صفحهٔ خالی، بدون اسکلت بارگذاری.
- آدرس غلط کالا = صفحهٔ ۴۰۴ پیش‌فرض، بدون راه برگشت به فروشگاه.

برای فروشگاهی که ترافیکش از گوگل می‌آید، صفحهٔ سفید یعنی از دست دادن سفارش و
افت رتبه.

**اقدام:** سه فایل ساده: `error.tsx` (با دکمهٔ «تلاش دوباره»)، `loading.tsx`
(اسکلت شبکهٔ کالا)، `not-found.tsx` (جست‌وجو + لینک دسته‌ها). نیم‌روز کار،
اثر زیاد.

### ج) کاتالوگ صفحهٔ اول برای گوگل خالی است (متوسط)

`src/app/shop/page.tsx` کاتالوگ را با `Suspense` و کامپوننت کلاینتی
`CatalogHome` رندر می‌کند؛ HTML اولیه فهرست کالا ندارد. تنها چیزی که گوگل
می‌بیند متن ثابتِ `ShopSeoText` است (که خوب نوشته شده، ولی جای کالا را نمی‌گیرد).

**اقدام (انتخاب یکی):**
1. ارزان: اولین صفحهٔ کاتالوگ را سروررندر کن (همان query، بدون فیلترهای
   تعاملی) و بقیه را کلاینتی ادامه بده.
2. درست‌تر: `generateMetadata` برای صفحهٔ کاتالوگ + `ItemList` JSON-LD.

### د) سئوی خانه و متادیتای پایه، عمومی است (متوسط)

`src/app/layout.tsx`:

```
title: "فروشگاه اینترنتی"
description: "فروشگاه اینترنتی — سفارش آنلاین"
```

نه نام فروشگاه، نه شهر، نه دستهٔ کالا. صفحهٔ کالا عالی است ولی صفحهٔ اول — که
بیشترین ورودی گوگل را دارد — ضعیف‌ترین است. همچنین `openGraph` و
`twitter` در layout تعریف نشده‌اند.

**اقدام:** `metadataBase` + الگوی `title.template`، `openGraph` پیش‌فرض با
تصویر، و نام فروشگاه از تنظیمات (همان `getShopName()` که در صفحهٔ کالا هست).

### ه) پرداخت آنلاین ندارد (متوسط — بسته به تصمیم کسب‌وکار)

تنها دو روش: `ON_DELIVERY` و `TRANSFER` (`checkout-view.tsx`). برای فروش
قطعات و سفارش‌های کم‌مبلغ، «کارت‌به‌کارت» نرخ تبدیل را می‌خورد؛ برای سفارش‌های
سنگین، درگاه لازم نیست.

**اقدام:** تصمیم صریح بگیر: اگر درگاه می‌خواهی، همان زمان «تأیید دستی رسید»
را هم نگه دار (چون درگاه‌ها قطع می‌شوند). اگر نمی‌خواهی، در صفحهٔ تسویه توضیح
بده که چرا — ابهام، سبد را رها می‌کند.

### و) یک تست برای ۷٬۲۰۰ خط (متوسط)

فقط `currency.test.ts`. منطق‌های حساسِ بدون تست: محاسبهٔ قیمت نهایی/تخفیف/
ارسال در `checkout-view.tsx`، وضعیت موجودی، و نرمال‌سازی ورودی فارسی.

**اقدام:** تست روی سه تابع خالص (قیمت سبد، تخفیف، هزینهٔ ارسال) + یک تست
smoke برای `apiFetch`. این‌ها ارزان‌اند و بیشترین باگ را می‌گیرند.

### ز) پیکربندی، به محیط گره خورده (کم)

- `allowedDevOrigins: ["10.141.233.130", "192.168.1.136"]` — IP هاردکد.
- هیچ `.env.example` برای سایت نیست (فقط `apps/api/.env.example` و ریشه).
  متغیرهای لازم: `SITE_API_URL`, `SITE_URL`, `SITE_API_PUBLIC_URL`,
  `NEXT_PUBLIC_SITE_API_PORT`.
- `reactStrictMode: false` — اثرهای دوگانه در توسعه دیده نمی‌شوند، پس باگ‌های
  پاک‌سازی (cleanup) پنهان می‌مانند.

**اقدام:** `.env.example` + یک README کوتاهِ استقرار؛ `allowedDevOrigins` از
متغیر محیطی؛ روشن‌کردن `reactStrictMode` و رفع هشدارها.

### ح) پنل فروشگاه داخل همان اپ است (کم، ولی برای فروش مهم)

`/admin` با همان بیلدِ فروشگاه سرو می‌شود. برای یک مشتری خوب است (یک استقرار،
یک دامنه)؛ برای فروش به چند مشتری، یعنی هر مشتری باید بیلد جدا بگیرد.

**اقدام در فاز بعد:** مسیر ادمین با احراز نقش محافظت شود (اگر هست، تست شود) و
در نقشهٔ راه «چند-فروشگاهی» به‌عنوان یک قلم مستقل ثبت شود.

## ۴) کارهایی که پیشنهاد می‌کنم همین هفته انجام شود

| # | کار | زمان | چرا اول این |
|---|---|---|---|
| ۱ | `error.tsx` + `loading.tsx` + `not-found.tsx` | ۰٫۵ روز | جلوی صفحهٔ سفید در ترافیک واقعی را می‌گیرد |
| ۲ | جاب `site` در CI + `typecheck:site` | ۰٫۵ روز | بدون این، هر تغییر بعدی ریسک است |
| ۳ | متادیتای layout (نام فروشگاه، OG، `metadataBase`) | ۰٫۵ روز | ارزان‌ترین بهبود سئو |
| ۴ | تست سه تابع قیمت/تخفیف/ارسال | ۰٫۵ روز | پول مشتری است؛ خطا در آن گران است |
| ۵ | `generateMetadata` + `ItemList` برای کاتالوگ | ۱ روز | ورودی گوگل به صفحات دسته |

جمع: حدود سه روز کاری، بدون تغییر در معماری. بعد از این‌ها، سایت از «کار
می‌کند» به «قابل سپردن به مشتری بزرگ» می‌رسد.

## ۵) آنچه عمداً بررسی نشد

- امنیت نفوذی (pen-test) و بارگذاری (load test) — نیاز به محیط و ابزار جدا دارد.
- کیفیت تصاویر و بهینه‌سازی حجم (چون `unoptimized` است، تصمیم معماری است نه باگ).
- تطابق کامل با الزامات مالیاتی فاکتور فروشگاه (نیاز به بررسی حقوقی).

این‌ها در فاز «آماده‌سازی سازمانی» دوباره دیده می‌شوند.
